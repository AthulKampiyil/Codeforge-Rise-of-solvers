# CodeForge decisions

Updated: 2026-10-12. Record material new decisions here; do not erase earlier rationale.

| Decision | Context / alternatives | Consequence and follow-up |
|---|---|---|
| Codeforces-only v1; LeetCode/CodeChef deferred | SRS §2.9 permits deferral when workable access is unavailable. Other provider enum entries are not adapters. | Only advertise and accept verified Codeforces as supported. Do not simulate judge history or bypass access controls. |
| Preserve actual TypeScript/Vite/Phaser 4.2.1 architecture | SRS/SADD describe React+Phaser; master prompt presumed React/Tailwind/Phaser 3, but `package.json`, entry and UI show otherwise. Wholesale migration risks the working village. | Record stack variance against SRS; improve existing shell incrementally unless a later explicit compliance decision requires React. |
| PostgreSQL remains durable correctness authority; Redis is optimization/transport | SADD v1.1 §7.2.1 makes cooldown durable; some older diagrams/prose disagree. Phase 1A applied same principle to auth and territory events. | No Redis-only session revocation, ownership or scoring authority. Outbox publication may retry/duplicate; clients must reconcile authoritative state. |
| Attack cooldown enforced from launch | Prevents parallel attacks; SADD §7.2.1 and current code. SRS §4.4.2 describes post-completion/abandonment timing. | Preserve current behavior while explicitly tracking SRS wording conflict; do not silently change user-facing duration/reset rules. |
| Preserve existing five-percent incumbent territory hysteresis pending product reconciliation | SADD §7.3.1.2/current implementation; SRS §5.5 states highest aggregate. | Test current rule, ties/no incumbent/concurrency; do not invent another formula. |
| Minimum five-minute manual sync in every environment | Explicit SRS REQ-2.2 and master prompt override previous demo-mode zero default. | Default and production validation require ≥300 seconds; independent-session endpoint contention test passes. Scheduled sync and attack proof scans remain separate. |
| Sync status describes actual activity, not just work becoming due | REQ-2.4 requires truthful status. A due full reconciliation previously appeared `in_progress` and could mask a failed log. | Preserve failed/up-to-date status until queued/running; expose reconciliation due separately. Tested with M2 status fixtures. |
| Earned topic level owns the structure's appearance | REQ-3.2 requires solve-derived level to change the village structure. Purchased M10 outpost tier had controlled art/scale instead. | Use earned-level art/scale and muted level-zero presentation; keep purchased tier as separate plinth/label cue. No change to scoring or purchases. |
| Start shared game-style visual language from current CP shell | Existing CP workflows are functional but visually separate from grassy Phaser village. Wholesale framework migration would risk them. | Reusable CSS materials/panels/buttons/auth states in existing DOM stack; preserve handlers. Desktop/mobile browser screenshots and remaining-tab review required. |
| Explicit leadership transfer keeps former leader as ordinary member | Current M5 prevents a leader leaving without succession, and user requires transfer. Alternative of deleting old leader risks orphaned guild/history. | Only current leader may transfer to existing member; transaction plus partial unique index protect against two leaders. Migration 022 requires duplicate-leader precheck. Guild-before-zone lock order corrected observed rescore/leave deadlock; focused/full tests pass on fresh test DB. |
| Public standings expose global only to guests | SRS §2.3 permits public leaderboard; prior guild scope swallowed an M5 method error and returned global results. | Guest may read safe global fields. Guild scope requires authenticated active membership and must never silently fall back to global. Backend and mocked desktop/mobile UI tests pass; live response remains unverified. |
| Do not equate War Room current share with recent earned contribution | SRS REQ-6.3 says recent contribution; SADD M5 applies sync-age decay, while current M6 uses undecayed topic levels divided by a potentially stale persisted guild score. No member history is stored. | Keep REQ-6.3 partial. A conservative future design is dated M5-owned scoring snapshots with applied member breakdown in same transaction as aggregate/ownership/outbox; product must approve whether recent observations satisfy the requirement. Do not fabricate historical rewards or a time window. |
| Preserve current village, remove reachable legacy actions incrementally | Phase 1B keeps shared renderer/art but blocks local gameplay. Replacing Phaser would risk visual/interaction regression. | Continue server-authoritative projection; measure bundle/runtime separately. Legacy source still shipped is not evidence it executes. |
| Retain M10 until product decision | Existing solve rewards and village snapshots depend on M10; deleting tables/UI blindly risks data and boot. | No new construction timers/costs. Distinguish earned topic strength from purchased visual tiers. |
| Phase 1A migration 021 is a forced-reauth cutover | Empty `auth_sessions` table rejects old JWT sessions. Mixed-version nodes would undermine durable revocation. | Apply migration before new nodes, drain old API/WebSocket nodes, require re-login; do not downgrade to Redis-only auth without revocation plan. No production rollout authorized. |

## Unresolved decisions — do not guess

- Identity unlink, retained solve provenance, relink/closure and duplicate reward policy (REQ-1.5).
- Territory activity decay based on verified practice versus last successful sync; current code uses sync age, which auto-poll can distort.
- Guild size/creation eligibility, leadership succession, exact trophy milestone values, and account deletion retention.
- Asset redistribution rights, production infrastructure/restore ownership, and measured NFR acceptance environment.
